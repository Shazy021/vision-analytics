# vision-bench — внешний автобенчмарк платформы

Отвечает на три вопроса, которые нельзя надёжно закрыть «на глаз»:

1. **Какую устойчивую нагрузку система держит?** — до какой ступени подачи
   латентности в бюджете и очереди не растут (max sustainable), где начинается
   коллапс.
2. **Где именно система упирается?** — какая стадия съедает бюджет времени и
   чья очередь растёт (yolo-инференс? декод? запись в PostgreSQL? реплики
   yolo-consumer?).
3. **Что изменилось после оптимизации?** — сравнение двух прогонов: сдвиг
   максимума, латентности на общих ступенях, сместилось ли узкое место.

Инструмент работает **строго снаружи** — теми же интерфейсами, что и
пользователь системы: HTTP API (`:8000`) и Prometheus (`:9090`). Код
приложения не модифицируется вообще: ни строчки в `app/`, ни новых метрик.

```
┌─────────────┐  POST /api/streams                                ┌──────────┐
│  vision-bench│ ─────────────────────────────────────────────────▶│  API     │
│  (хост)      │                                                   └──────────┘
│             │  PromQL: increase / лаги / гистограммы окном       ┌──────────┐
│  ramp → окна │ ◀──────────────────────────────────────────────── │Prometheus│
│  → drain     │   (ретроспективно, с явным `at`)                  └──────────┘
└─────────────┘
        │ RTSP (ffmpeg → MediaMTX :8554)
        ▼
   «камеры» для N стримов платформы
```

## Быстрый старт

```bash
# 0) зависимости (в venv репозитория)
pip install -e ".[bench]"

# 1) убедиться, что сам инструмент исправен — 2 минуты, docker НЕ нужен:
python -m bench selftest

# 2) поднять стек платформы и проверить готовность
make up
python -m bench preflight --video path/to/clip.mp4

# 3) стримовый прогон (ramp «камерами»): ~30 минут на default-профиле
python -m bench run --profile default \
    --video path/to/clip.mp4 --label "baseline"

# 4) после оптимизации — второй прогон и сравнение
python -m bench run --video path/to/clip.mp4 \
    --label "yolo-batch-8" --notes "батч инференса 8 в yolo consumer"
python -m bench compare bench/results/stream-<до>/ bench/results/stream-<после>/
```

Результат каждого прогона — каталог `bench/results/<run_id>/`:
`result.json` (полные данные, машина-читаемые), `report.md` (человекочитаемый
отчёт), `load_curve.png` (латентность и рост лага по ступеням).

## Как устроен прогон

Каждая ступень ramp'а проходит один и тот же цикл:

```
применить нагрузку → settle (прогрев) → окно измерения → анализ из Prometheus
```

Один ffmpeg на хосте публикует клип в MediaMTX (`rtsp://localhost:8554/bench/src`),
платформенные producer'ы читают его внутри docker-сети
(`rtsp://mediamtx:8554/bench/src`). MediaMTX разводит один поток на всех
читателей — N «камер» без N файлов. Ступени — число активных стримов
(`--scale streams`, offered = N × fps) или fps одного стрима (`--scale fps`,
стрим пересоздаётся на каждой ступени).

**Все измерения — ретроспективные запросы к Prometheus с явным моментом
`at`** (конец окна): окно зафиксировано границами времени, а не моментом
запроса. Поэтому анализ шага не соревнуется со следующей ступенью нагрузки,
а скорости считаются приростом счётчиков ровно за окно (`increase`) — без
хвоста предыдущей ступени, который затаскивало бы скользящее окно `rate()`.

После последней ступени меряется **drain**: подача прекращается, и видно,
за сколько система разгребает накопленный бэклог (лаги Kafka). Это честная
цена «продержались на грани» — ступень может быть формально устойчивой в
окне, но с многометровым хвостом очереди.

## Критерий «система держит нагрузку»

Вердикт шага = все квитанции пройдены на окне измерения:

| Конвейер | Квитанции | Что ловит |
|---|---|---|
| стримы | e2e p95 ≤ 2с; лаг yolo/detection растёт ≤ 0.5 сообщ/с; обработка ≥ 95% подачи | латентность пользователю, рост бэклога, отставание консьюмеров |

**Итог прогона**: max sustainable — последняя устойчивая ступень (разрешение
равно шагу лестницы: ступени 20 и 40 fps не отличат ёмкость 25 от 35 —
уточняй `--streams/--fps`), collapse — первая неустойчивая. Если неустойчивых
нет — система не насыщена в проверенном диапазоне.

**Атрибуция узкого места** — «бюджет времени ключевой латентности»: e2e
(захват кадра → коммит в БД). Она раскладывается на стадии
(`frame_*_duration_seconds`, ожидания в топиках); чья доля доминирует
ИЛИ чья очередь растёт — тот и упирается. Точка коллапса говорит ГДЕ сломалось,
бюджет на устойчивом максимуме — ЧТО дорожает.

## Профили

| Профиль | Ступени | Окна | Время* |
|---|---|---|---|
| `quick` | 1,2,4,8 стримов @ 5fps | 20+45с | ~10 мин |
| `default` | 2,4,6,8,12,16,24 стримов @ 5fps | 25+90с | ~28 мин |
| `thorough` | 1..48 стримов @ 5fps | 40+180с | ~2ч |

\* стримы дольше из-за развёртывания: reconciler платформы подтверждает
`active` только через HEALTHY_THRESHOLD=30с — это честное время разворота
нагрузки, а не оверхед бенчмарка. Любые параметры переопределяются флагами
(`--streams '2,4,6'`, `--fps 10`, `--settle`, `--measure`).

## Команды

```
python -m bench run         прогон (см. флаги ниже)
python -m bench compare A B отчёт «до → после» по двум result.json (+ график)
python -m bench preflight   проверки стенда без прогона (API, Prometheus-таргеты,
                            ffmpeg, ролик, окружение)
python -m bench cleanup     удалить созданные бенчмарком стримы (по префиксу
                            bench-cam-; пользовательские данные не трогает)
python -m bench selftest    проверка самого инструмента против мока с ИЗВЕСТНОЙ
                            ёмкостью (без docker, ~2 минуты)
```

Ключевые флаги `run`: `--profile`, `--label`,
`--notes` (что менял — попадёт в отчёт и compare), `--video` (ролик-источник;
один и тот же для сравнимости прогонов), `--mock`, `--keep-artifacts`,
`--no-drain`, `--skip-preflight`, `--out-dir`.

Адреса стенда — флагами `--api-url/--prom-url/--rtsp-publish/--rtsp-source`
или переменными окружения `BENCH_API_URL`, `BENCH_PROM_URL`,
`BENCH_RTSP_PUBLISH`, `BENCH_RTSP_SOURCE` (дефолты — localhost).

## Метрики (все уже существуют в платформе)

| Что | Метрика |
|---|---|
| e2e кадра (захват → коммит в БД) | `frame_e2e_latency_seconds` |
| ожидание в топике | `frame_queue_wait_seconds{topic=raw_frames/detections}` |
| стадии кадра | `frame_decode/inference/write_duration_seconds` |
| приём/обработка кадров | `frames_received_total`, `frame_processed_total{result}` |
| бэклог консьюмеров | `kafka_consumergroup_lag{consumergroup}` |

Группы консьюмеров: `yolo-workers`, `detection-writer`.
Порты `/metrics` консьюмеров (:9091-93) наружу не проброшены — единственный
внешний наблюдатель это Prometheus, и бенчмарк читает ровно то, что видит
пользователь системы.

## Selftest: почему ему можно верить

`python -m bench selftest` поднимает локальный HTTP-мок (`bench/mock_stack.py`),
повторяющий наружное поведение платформы (REST API + PromQL) с **известной
пропускной способностью**: 30 fps стримов. Прогон ищет границы вслепую — если
найдена именно эта (коллапс на 40 fps), значит оркестратор, окна, квантили,
лаги и вердикты работают правильно. Дополнительно проверяются preflight,
артефакты и compare.

Мок полезен и как регрессионный тест при развитии самого бенчмарка
(CI: `python -m bench selftest; echo $?`).

## Ограничения и честные оговорки

- Точность границ окна ± один скрейп Prometheus (15с на дефолте).
- Разрешение max sustainable = шаг лестницы ступеней.
- Ролик-источник должен быть одним и тем же между сравниваемыми прогонами
  (клип ре-кодируется детерминированно: H.264 veryfast/CRF23, кэш по sha256).
- Часы хоста бенчмарка и стенда должны быть синхронизированы (NTP): окна
  задаются эпохой хоста.
- Теги `--label/--notes` — единственный способ связать прогон с изменением
  системы; заполняй их дисциплинированно.

## Структура

```
bench/
├── config.py       профили, критерии, эндпоинты (env-переопределяемые)
├── models.py       схемы result.json: шаги, итоги, вердикты
├── api_client.py   REST-клиент: ровно те вызовы, что делает пользователь

├── load_stream.py  ступени «камер» через API (scale=streams|fps)
├── analysis.py     измерение шага, вердикты, атрибуция узкого места
├── runner.py       оркестратор: ramp → окна → drain → teardown
├── reports.py      result.json, report.md, load_curve.png
├── compare.py      отчёт и график «до → после»
├── preflight.py    проверки стенда до прогона (fail fast)
├── mock_stack.py   синтетический стенд для selftest
├── selftest.py     проверка инструмента против мока
└── cli.py          python -m bench ...
```
